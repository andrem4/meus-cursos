Capítulo 1

O que é DevOps?

DevOpsDevOpsJunção de "Development" (desenvolvimento) e "Operations" (operações). Conjunto de práticas que aproxima quem escreve código de quem mantém a infraestrutura rodando, com o objetivo de entregar software confiável em ritmo rápido e constante. nasceu como resposta a um problema muito concreto: equipes de desenvolvimento, teste e operações que trabalhavam isoladas, jogando o trabalho "por cima do muro" umas para as outras, cada uma com metas conflitantes — devs queriam entregar rápido, testadores queriam achar o máximo de defeitos, operações queria o máximo de estabilidade (e toda atualização é risco de queda). O resultado histórico: software cheio de bugs, atrasado, e equipes frustradas culpando-se mutuamente.

🏢 No condomínio

Imagine um condomínio antigo onde o pedreiro constrói, o síndico só aprova depois de pronto, e o zelador só recebe a chave no fim — sem conversar entre si durante a obra. Se algo desanda, cada um culpa o outro. DevOps é trocar isso por uma equipe única e multidisciplinar que já nasce responsável pelo edifício inteiro, do projeto à entrega das chaves — dividindo o mesmo painel de metas.

Um pouco de história

O termo foi cunhado há mais de uma década. A primeira conferência dedicada ao tema, a devopsdays, aconteceu em Ghent, na Bélgica, em 2009. O primeiro relatório "State of DevOps" saiu em 2012, e desde 2014 passou a ser publicado anualmente, período em que a adoção do DevOps acelerou fortemente. Tecnologias como virtualizaçãoVirtualizaçãoTécnica que permite rodar múltiplos ambientes de computador (máquinas virtuais) isolados sobre um único hardware físico., nuvem e containerizaçãoContainerizaçãoEmpacotar uma aplicação com tudo o que ela precisa para rodar (bibliotecas, configurações) em uma unidade isolada e portátil, chamada container. mudaram as expectativas: tudo precisa funcionar sem downtime (tempo fora do ar) e sob demanda.

Os fundamentos do DevOps

Apesar de a conversa girar em torno de ferramentas, DevOps é, na essência, cultura organizacional. Times deixam de ser definidos pelo tipo de trabalho que fazem (um time só de devs, outro só de testadores) e passam a ser definidos pelo resultado que entregam — um mesmo time reúne desenvolvedor, testador, Scrum MasterScrum MasterPapel dentro do Scrum responsável por remover obstáculos do time e garantir que o processo ágil seja seguido., product ownerProduct Owner (PO)Pessoa responsável por priorizar o que deve ser feito, representando a voz do negócio/cliente perante o time técnico., analista de negócio, administrador de sistemas e engenheiro de segurança.

A adoção de metodologias ágeisMetodologias ágeis (Agile)Conjunto de práticas de gestão de projeto baseadas em ciclos curtos e entregas incrementais, em contraste com o modelo tradicional "Cascata" (Waterfall), onde tudo é planejado no início e entregue só no fim., como o ScrumScrumFramework ágil onde times pequenos (4 a 7 pessoas) trabalham em ciclos curtos chamados sprints, com reuniões diárias curtas para acompanhar o progresso., ajuda a acelerar ainda mais essa entrega. A ideia central do Scrum: times pequenos trabalham em sprintsSprintPeríodo fixo de trabalho (normalmente 2 a 3 semanas) no qual um conjunto de tarefas planejadas deve ser concluído e, idealmente, entregue. de duas a três semanas, com uma reunião diária curta (Daily Scrum) para alinhar o progresso. Periodicamente, o time olha os itens pendentes do backlogBacklogLista de tudo o que precisa ser feito no projeto, priorizada e ainda não realizada., estima o esforço necessário e o product owner ordena por prioridade — assim o time sabe quanto trabalho cabe no próximo sprint. Ao final de cada sprint, há uma retrospectiva: o que funcionou, o que pode melhorar.

Automação: a palavra-chave técnica

Quando desenvolvedores e administradores de sistemas trabalham juntos, o código pode passar a ser entregue automaticamente. Ferramentas como o próprio Azure DevOps, GitHub, GitLab, Jenkins e Bamboo cumprem esse papel. O fluxo típico:

  1. O código é enviado (commit) para o controle de versão GitGitSistema de controle de versão distribuído — cada desenvolvedor tem uma cópia completa do histórico do código. Padrão de fato da indústria..
  2. Um build (compilação/montagem) é disparado automaticamente no servidor.
  3. Se o build passa, o código é testado automaticamente com os testes unitários escritos pela equipe.
  4. Passando nos testes, o código é implantado (deploy) em um ambiente de homologação (staging) para testes manuais de aceitação.
  5. Aprovado, o código pode ser implantado em produção com um clique — e pouco ou nenhum downtime.

Esse processo de compilar e testar automaticamente chama-se Integração ContínuaIntegração Contínua (Continuous Integration, CI)Prática de compilar e testar automaticamente o código a cada alteração enviada ao repositório, detectando problemas cedo. (CI). O deploy automático depois disso é Entrega ContínuaEntrega Contínua (Continuous Delivery)Automatizar o deploy até um ambiente de pré-produção, deixando o software sempre pronto para ir a produção — a liberação final ainda pode ser manual. (também abreviada CD). Se absolutamente todos os passos manuais forem eliminados e o código vai do commit direto à produção, fala-se em Implantação ContínuaImplantação Contínua (Continuous Deployment)Variante mais radical da entrega contínua: nenhuma etapa manual — o código aprovado nos testes vai para produção sozinho.. Na prática, o termo genérico CI/CDCI/CDSigla que junta Integração Contínua e Entrega/Implantação Contínua — o conjunto completo de automação entre escrever código e colocá-lo em produção. é usado quase como sinônimo de DevOps.

O papel da nuvem

Com a popularização da computação em nuvemNuvem (Cloud computing)Modelo de fornecimento de infraestrutura e serviços de TI via internet, sob demanda, sem necessidade de hardware próprio., o DevOps — e especialmente o CI/CD — ficou muito mais fácil de praticar: recursos inteiros podem ser criados a partir de um script (JSONJSON (JavaScript Object Notation)Formato leve de texto para representar dados estruturados, muito usado em configurações e comunicação entre sistemas., PowerShellPowerShellLinguagem de linha de comando e automação da Microsoft, usada para gerenciar sistemas Windows e recursos Azure. ou CLICLI (Command-Line Interface)Interface de linha de comando — forma de interagir com um sistema digitando comandos de texto, em vez de clicar em uma interface gráfica.), sem intervenção manual. O próprio Azure DevOps é uma solução em nuvem, sucessora do antigo Team Foundation Server (TFS)TFS (Team Foundation Server)Antecessor on-premises (instalado localmente) do Azure DevOps, hoje renomeado para Azure DevOps Server., que rodava localmente ("on-premises").

Nuvem e DevOps juntos também abriram espaço para um novo padrão arquitetural: microsserviçosMicrosserviços (Microservices)Padrão de arquitetura onde uma aplicação grande é dividida em subsistemas menores e independentes, cada um com seu próprio banco de dados, que se comunicam entre si.. Em vez de uma aplicação única e monolítica, o sistema é dividido em módulos independentes (ex.: módulo de produtos, de vendas, de estoque, financeiro), cada um escalável e substituível separadamente. A vantagem é a escalabilidade e a resiliência (se um módulo cai, os outros continuam); a desvantagem é a multiplicação de implantações — o que só se torna administrável com CI/CD bem automatizado. Ferramentas de containerização como DockerDockerFerramenta que empacota aplicações em containers — ambientes isolados e portáteis que rodam de forma consistente em qualquer máquina. e KubernetesKubernetesSistema de orquestração de containers: gerencia automaticamente onde e como containers são executados, escalados e recuperados em caso de falha. ajudam a administrar esse cenário mais complexo.

⚠ Cultura não é só rótulo

Chamar-se de "Ágil" enquanto a operação continua desorganizada, ou dizer que "faz DevOps" só porque existe um pipeline de CI rodando, não é DevOps. A mudança real está na cultura: times multifuncionais assumem responsabilidade compartilhada pelo código e pelo ambiente. Quando um bug aparece em produção, o objetivo não é apontar culpados — é resolver o problema o quanto antes, seja qual for a origem. Esse mesmo espírito colaborativo, sem cultura de "nomear e envergonhar", deve se estender também a usuários e à gestão, que participam do processo de desenvolvimento desde cedo.

Onde o Azure DevOps entra nisso tudo

O Azure DevOps é a caixa de ferramentas que dá suporte técnico à cultura DevOps. Ele reúne cinco grandes áreas, que serão o roteiro do restante deste guia:

  • Boards — times criam e priorizam histórias de usuário, estimam esforço e planejam sprints.
  • Repos — código-fonte sob controle de versão Git, vinculado a itens de trabalho, com revisão de código obrigatória.
  • Pipelines — automação de build e release (CI/CD); o código pode vir do próprio Azure Repos, do GitHubGitHubPlataforma de hospedagem de código baseada em Git, hoje também propriedade da Microsoft., do Bitbucket Cloud ou de outros; suporta praticamente qualquer linguagem (.NET, Java, Go, JavaScript, Python, entre outras) e sistemas operacionais (Windows, Ubuntu, macOS).
  • Test Plans — testadores criam, executam e documentam planos de teste manuais.
  • Artifacts — pacotes de software reutilizáveis, com suporte a gerenciadores como NuGetNuGetGerenciador de pacotes para o ecossistema .NET — permite reutilizar bibliotecas de código já compiladas., npmnpm (Node Package Manager)Gerenciador de pacotes padrão do ecossistema JavaScript/Node.js., MavenMavenFerramenta de build e gerenciamento de dependências para projetos Java. e pippipGerenciador de pacotes padrão da linguagem Python..
ℹ Resumo do capítulo

DevOps é, antes de tudo, um jeito de trabalhar: colaboração entre times antes separados, entregando software confiável em ritmo previsível. O Azure DevOps entrega o "pacote completo" — planejamento, controle de versão, automação de build/release e gestão de testes — em um único produto, enquanto ferramentas concorrentes normalmente cobrem só uma ou duas dessas frentes.

Configurando o Azure DevOps

Antes de usar o Azure DevOps é preciso montar a base: uma conta MicrosoftConta MicrosoftIdentidade usada para acessar serviços da Microsoft (Outlook, Azure, Azure DevOps, etc)., um tenant do AzureTenant (Azure Active Directory)Um "container" que reúne usuários, contas e assinaturas de uma organização dentro do Azure. É a identidade corporativa/organizacional na nuvem da Microsoft., uma assinatura e, por fim, a organização e o projeto dentro do Azure DevOps propriamente dito. O Azure e o Azure DevOps são gratuitos para começar, mas a criação da conta Azure exige um cartão de crédito (mesmo em contas que nunca chegam a ser cobradas).

🏢 No condomínio

Criar o tenant do Azure Active Directory é como abrir o CNPJ da administradora que vai tocar o condomínio — é o "documento-mãe" que identifica juridicamente todo mundo que mora ali. A assinatura (subscription) é a conta bancária vinculada a esse CNPJ, de onde saem os pagamentos dos serviços contratados (água, luz, portaria). A organização do Azure DevOps é o próprio condomínio erguido sobre esse CNPJ, e cada projeto é um edifício dentro dele.

Criando uma conta Microsoft e um tenant do Azure

O processo de cadastro passa por criar (ou reaproveitar) uma conta Microsoft — inclusive é possível entrar com uma conta pessoal do GitHub — e, em seguida, criar um Azure Active Directory (Azure AD / AAD)Azure Active Directory (Azure AD ou AAD)Serviço de identidade e gerenciamento de acesso da Microsoft. É o coração da conta Azure: nele ficam os usuários, o nome e o ID do tenant.. O plano gratuito de teste do Azure libera alguns serviços populares (como 5 GB de armazenamento) e um crédito inicial em dinheiro para usar em serviços pagos por um tempo limitado. Um ponto importante: o Azure cobra por uso — se uma máquina virtual custaria R$500/mês mas você a apaga na metade do mês, paga só R$250.

ℹ Cobrança e sempre-gratuitos

Alguns recursos do Azure são sempre gratuitos, independente de plano: ofertas serverless (sem servidor dedicado), a camada gratuita do App Service e o próprio Azure Active Directory.

Azure Active Directory

É no Azure AD que fica o nome e o ID do tenant, além da lista de usuários (os mesmos que depois serão adicionados no Azure DevOps). O nome padrão do diretório pode ser alterado nas Propriedades — útil porque, se o cadastro foi feito com uma conta Outlook, o nome inicial do tenant costuma ser algo pouco amigável, do tipo seuemail_outlook_numero.onmicrosoft.com.

Criando a conta e a organização no Azure DevOps

Com a conta Microsoft já vinculada ao Azure, criar a conta do Azure DevOps é rápido — o sistema pede apenas confirmação de país e algumas preferências. Você chega então à sua organização padrão (nomeada automaticamente com base no seu e-mail), e a partir dali pode criar um projeto: nome, descrição, visibilidade (pública ou privada) e, nas configurações avançadas, o tipo de controle de versão e o processo de item de trabalhoProcesso de item de trabalho (Work item process)Template que define quais tipos de cartão de tarefa (épico, história, bug, etc.) e quais colunas de fluxo o projeto vai usar: Basic, Agile, Scrum ou CMMI. (Basic, Agile, Scrum ou CMMICMMI (Capability Maturity Model Integration)Modelo de maturidade de processos mais formal e burocrático, com tipos de item de trabalho adicionais; pouco usado fora de ambientes muito regulados.).

⚠ Git vs. TFVC

Nas configurações avançadas do projeto, o controle de versão pode ser Git ou Team Foundation Version Control (TFVC). O TFVC é um sistema centralizado mais antigo; desde agosto de 2024 ele nem sequer é mais oferecido para novos projetos, como reforça um dos slides do material de apoio. O Git — sistema distribuídoControle de versão distribuídoModelo em que cada desenvolvedor tem uma cópia completa do histórico do repositório em sua própria máquina, ao contrário do modelo centralizado, onde só o servidor guarda o histórico completo. — é hoje o padrão de fato da indústria e é a escolha recomendada, salvo necessidade específica.

Passo a passo prático — criar um novo projeto (conforme os slides)

  1. Acesse https://dev.azure.com e clique em Create a project to get started.
  2. Preencha um Name (nome) e uma Description (descrição) significativos.
  3. Em Advanced, defina Version control = Git e Work item process = Scrum.
  4. Clique em Create project.

Organizando projetos: um ou muitos?

Cada organização pode ter vários projetos, e cada projeto pode ter vários repositóriosRepositório (Repository)Local onde o código-fonte de uma aplicação é armazenado e versionado com Git. e boardsBoardQuadro visual (estilo Kanban) para acompanhar itens de trabalho em colunas de status.. Não existe uma regra fixa: equipes com múltiplos clientes costumam separar por cliente; equipes com sistemas relacionados (ex.: ERP e CRM que compartilham serviços) podem optar por projetos separados com um projeto extra só para os serviços compartilhados, ou manter tudo em um único projeto com múltiplos repositórios. A decisão depende de como as equipes e o acesso de usuários estão organizados.

Gestão de usuários e níveis de acesso

Usuários são adicionados nas configurações da organização. Existem três níveis de acesso:

  • Basic — acesso completo a Boards, Repos e Pipelines. Cada organização tem direito a 5 usuários Basic gratuitos; usuários adicionais são cobrados por mês.
  • Stakeholder — acesso sempre gratuito e ilimitado, mas limitado: acesso completo a Pipelines, nenhum acesso a Repos e acesso restrito a Boards.
  • Visual Studio Subscriber — quem já paga uma assinatura profissional/enterprise do Visual Studio tem acesso completo sem ocupar uma vaga gratuita.

Além do nível de acesso à organização, cada usuário pode ser adicionado a um grupo dentro de um projeto específico: Readers (leitores), Contributors (contribuidores) ou Administrators (administradores). Como reforçam os slides, adicionar alguém apenas pela tela de convite do projeto costuma dar só acesso de leitura ("Stakeholder"); para dar acesso administrativo completo é necessário ir em Organization Settings → Users → Add users, definindo o Access level como Basic e marcando o projeto correto.

⚠ Cuidado com o papel de administrador

Um Project Collection AdministratorProject Collection AdministratorPapel com poder total sobre toda a organização do Azure DevOps: pode alterar usuários, permissões, conectar/desconectar o Azure AD e até remover outros administradores. tem poder irrestrito sobre a organização inteira — incluindo a capacidade de remover outros administradores. Atribua esse papel com extremo cuidado.

Faturamento (Billing)

Além dos 5 usuários gratuitos, o plano gratuito inclui 1.800 minutos (30 horas) de build por mês e um agente hospedado por vez — ou seja, jobs de build/release rodam em fila, um de cada vez. Para aumentar usuários, minutos de build ou jobs paralelos, é preciso vincular uma assinatura Azure com faturamento habilitado. A cobrança é diária: adicionar e remover um usuário no meio do mês cobra apenas os dias de uso.

Conectando o Azure Active Directory

Conectar a organização do Azure DevOps a um Azure AD centraliza a gestão de usuários (as permissões específicas do Azure DevOps continuam sendo atribuídas separadamente). É um processo que pode gerar friç­ões — usuários que não pertencem ainda ao mesmo Azure AD perdem acesso temporariamente e precisam ser reconectados manualmente ou via convite.

Configurações do projeto

Em Project Settings é possível renomear o projeto, mudar sua visibilidade, ativar/desativar serviços específicos (por exemplo, desligar Test Plans se a equipe não usa), adicionar administradores extras e excluir o projeto. Também é ali que se configuram service hooksService hooksIntegrações que notificam serviços externos (Slack, por exemplo) quando eventos específicos ocorrem no projeto, como um push de código ou a atualização de um item de trabalho., dashboards com widgets (como gráficos de burndown) e uma wiki para documentação interna.

Segurança e permissões

Em Organization Settings → Security encontram-se Policies (políticas gerais, como proibir projetos públicos) e Permissions (grupos e usuários). Os grupos padrão mais importantes são Project Collection Valid Users (o grupo mais amplo — todo mundo pertence a ele) e Project Collection Administrators (acesso total). A recomendação geral é não editar os grupos internos e, se necessário, criar grupos novos herdando as permissões desejadas.

📝 Bons hábitos ao configurar

Mudar o nome da organização muda também a URL de tudo (dev.azure.com/[nome]) — repositórios, feeds de pacotes, documentação e favoritos salvos por toda a equipe precisam ser atualizados. Planeje esse tipo de mudança com antecedência e, se possível, faça-a antes de o ambiente ter projetos em produção.

ℹ Resumo do capítulo

O Azure DevOps oferece controle detalhado sobre organização, projetos, usuários e permissões. A conexão com o Azure Active Directory centraliza a identidade dos usuários, e a assinatura Azure cuida do faturamento de recursos extras. Times de qualquer tamanho podem moldar essa estrutura conforme sua realidade.

Capítulo 3

Boards

Todo projeto do Azure DevOps nasce com um quadro KanbanKanbanMétodo visual de gestão de fluxo de trabalho, com colunas representando estágios (ex.: A Fazer, Em Progresso, Feito) e cartões que se movem entre elas. padrão. O Boards é onde o trabalho é planejado, priorizado, estimado e acompanhado.

🏢 No condomínio

O Boards é o quadro de avisos e o livro de obras do síndico: toda reforma grande (um épico) é dividida em pedidos de serviço (issues/histórias), e cada pedido de serviço em tarefas concretas para o zelador ou empreiteiro (tasks) — "trocar a fiação do 3º andar", "pintar a fachada". O quadro físico na portaria, com colunas "A Fazer / Em Andamento / Concluído", é exatamente o quadro Kanban do board.

Um item de trabalhoItem de trabalho (Work item)Unidade básica de planejamento no Azure Boards: pode ser um épico, uma história/issue, uma tarefa, um bug etc., dependendo do processo escolhido. é qualquer "cartão" no board. Um backlogBacklogLista priorizada de tudo o que ainda precisa ser feito no projeto. é simplesmente uma lista do que falta fazer, geralmente escrita por gerentes de projeto, product owners e/ou analistas de negócio. (1, 2, 3, 5, 8…) ou "tamanhos de camiseta" (PP, P, M, G, GG). O importante é que a estimativa seja relativa a um item de referência, não uma contagem literal de horas — embora, na prática, muitas equipes acabem usando horas de qualquer jeito.

Uma vez planejado, o sprint costuma ser tratado como compromisso — mudanças de prioridade no meio do caminho geram estresse e prejudicam a previsibilidade da equipe.

Os três processos: Basic, Agile e Scrum

O Azure DevOps oferece quatro "processos" (templates de item de trabalho) — Basic, Agile, Scrum e CMMI (este último fora do escopo deste guia). Cada um define uma hierarquia diferente de tipos de item:

Simulador — Hierarquia de itens de trabalho por processo

Processo Basic

O mais simples: Epic → Issue → Task. Um épico (epic) contém issues; uma issue contém tasks. Exemplo: "adicionar uma loja virtual ao produto" pode ser um épico; dentro dele, issues como "criar página de busca de produtos"; dentro da issue, tasks como "adicionar link para a loja na home".

ℹ Nota de terminologia

O termo epic vem do vocabulário ágil tradicional, onde originalmente significava "duas ou mais histórias de usuário juntas" — o sentido meio que se inverteu ao longo do tempo, e hoje "épico" é a unidade maior, não a soma de histórias menores.

Processo Agile

Hierarquia: Epic → Feature → User Story → Task (com Bugs e Tests também associados à User Story). O que era "issue" no processo Basic vira "user story" aqui. Existe ainda um tipo Issue separado no processo Agile, com um significado diferente: um bloqueio a um trabalho planejado ou a um release — por exemplo, "capacidade do servidor insuficiente para a nova carga esperada da loja virtual". Issues não aparecem automaticamente no backlog nem no board; para vê-las é preciso criar uma queryQueryFiltro salvo sobre os itens de trabalho — por exemplo, "tudo que está atribuído a mim" ou "issues ainda não resolvidas"..

Processo Scrum

Hierarquia: Epic → Feature → Product Backlog Item (PBI) → Task, com Impediment no lugar de Issue. A diferença mais notável: no Scrum, bugs ganham cartão próprio e aparecem no backlog e no board (no Agile, bugs ficam "dentro" das tasks, sem cartão visível separado).

Simulador — Feature → Product Backlog Item → Task

O quadro (Board) e o backlog

O board tradicional tem três colunas: To Do (a fazer), Doing ou In Progress (em andamento) e Done (concluído) — mas equipes frequentemente adicionam colunas como Test ou Deployed. Um cartão é arrastado entre colunas conforme o status muda. Uma boa prática citada no livro: cada desenvolvedor deveria trabalhar em, no máximo, um item por vez — o board costuma mostrar algo como "1/5" indicando quantas pessoas (de um limite configurado) estão numa coluna.

Simulador — Quadro Kanban (arraste os cartões)

Dentro de um cartão é possível abrir uma discussão, mencionar colegas com @nome (que recebem um e-mail) e vincular outros itens com # ou pull requests com !.

Customizando o board

É possível personalizar quais campos aparecem nos cartões, aplicar cores condicionais (ex.: cartões marcados com a tag "Blocked" ficam vermelhos), adicionar ou remover colunas, definir limites de WIPWIP (Work In Progress)Quantidade de itens que podem estar simultaneamente em uma coluna/estágio do fluxo — limitar o WIP evita que o time acumule trabalho "em andamento" demais ao mesmo tempo. por coluna e criar swimlanesSwimlaneDivisão horizontal do quadro Kanban, útil para destacar itens de prioridade diferente (ex.: uma faixa exclusiva para itens urgentes) sem precisar criar uma coluna nova. (raias horizontais) — por exemplo, uma raia dedicada a itens urgentes, cruzando todas as colunas.

Trabalhando em sprints

Um projeto Scrum vem com seis sprints já planejados por padrão. Itens do backlog são arrastados para dentro de um sprint específico; o quadro de tarefas do sprint (taskboard) mostra apenas os itens daquele ciclo, permitindo o dia a dia de arrastar tarefas entre "A Fazer", "Em Progresso" e "Feito". A aba Capacity permite planejar quantas horas cada pessoa do time pode dedicar por dia — informação que alimenta o gráfico de BurndownGráfico de BurndownGráfico que mostra o esforço restante em um sprint ao longo do tempo, comparando o planejado com o real — ajuda a visualizar se a equipe está "queimando" o trabalho no ritmo esperado., que compara o trabalho planejado, a capacidade real e o esforço restante dia a dia.

💬 Do livro

Em um sprint perfeito, as três linhas do burndown (planejada, capacidade e restante) andariam coladas — mas isso quase nunca acontece. Segundo o autor, o padrão mais comum é a linha de trabalho restante cair rápido no início (tarefas fáceis, superestimadas), subir um pouco no meio (quando surgem pendências) e cair abruptamente perto do fim, quando todos correm para fechar suas tarefas.

Customizando o processo

É possível criar um processo herdadoProcesso herdado (Inherited process)Cópia personalizável de um processo padrão (Basic, Agile, Scrum), que permite adicionar campos e tipos de item de trabalho próprios sem alterar o template original da Microsoft. a partir de Basic, Agile ou Scrum, adicionando tipos de item de trabalho customizados (por exemplo, um tipo "Supplier Issue" com um campo de data de entrega estimada) e até novos níveis de backlog. Só depois de adicionar o novo tipo ao nível de backlog correto (em Backlog levels) ele passa a aparecer no board e no backlog.

Múltiplos boards em um projeto

Criando times (Teams) dentro de um mesmo projeto, é possível ter múltiplos boards — por exemplo, um "Back-end Team" com seu próprio board, sprints e configurações, dentro do mesmo projeto Scrum. Não é possível, porém, ter processos diferentes para times diferentes dentro de um mesmo projeto.

ℹ Resumo do capítulo

O Boards organiza o trabalho em itens hierárquicos (épico → feature/user story/PBI → task), estimados e planejados em sprints, e visualizados tanto no backlog quanto no quadro Kanban. A customização de processos e a criação de múltiplos times tornam o Boards adaptável a praticamente qualquer fluxo de trabalho.

Capítulo 4

Repositórios (Repos)

Planejamento é só metade da história — em algum momento a equipe precisa entregar código. O ReposReposMódulo do Azure DevOps para controle de versão de código-fonte, baseado em Git. é onde times de qualquer tamanho compartilham código, versionam alterações e revisam o trabalho uns dos outros.

🏢 No condomínio

O Repos é o depósito central de plantas e documentos técnicos do condomínio, com um livro de registro de cada alteração feita na planta original — quem mudou o quê, quando e por quê. Cada branch é uma cópia de rascunho da planta onde um engenheiro pode testar uma modificação sem mexer na planta oficial (a branch principal, historicamente chamada master). Só depois de aprovada (via pull request) a alteração é incorporada à planta definitiva.

Repositórios e o clone local

Um projeto pode ter múltiplos repositórios — natural em cenários de microsserviços, onde cada serviço tem seu próprio código. Um novo projeto já nasce com um repositório padrão vazio, que pode ser inicializado com um arquivo README.md e um .gitignore apropriado à tecnologia usada (o slide de apoio recomenda, por exemplo, o template "VisualStudio" para projetos .NET).

ℹ .gitignore

O arquivo .gitignore diz ao Git quais arquivos e pastas não devem ser versionados — tipicamente pastas geradas automaticamente pelo processo de build (como bin e obj em projetos .NET), que não fazem sentido guardar no histórico.

O repositório pode ser clonado (copiado para a máquina local) diretamente do botão Clone, com suporte nativo a Visual Studio, Visual Studio Code, Android Studio, Eclipse, entre outros — ou via URL HTTPS/SSH para qualquer outra ferramenta.

Branches: locais e remotas

Uma branchBranch (ramificação)Linha de desenvolvimento paralela dentro do repositório Git, que permite trabalhar em uma alteração sem afetar o código principal até que ela esteja pronta. local existe só na máquina do desenvolvedor; ao ser enviada (push) para o Azure DevOps, torna-se uma branch remota, compartilhável com o time. Branches sem novos commits há mais de três meses são sinalizadas como staleStale branchBranch "parada" — sem novos commits há um tempo prolongado (o Azure DevOps usa três meses como referência), sinal de que pode estar abandonada. (obsoletas).

Merge e Pull Requests

Unir uma branch de volta à principal é feito por meio de um pull requestPull Request (PR)Solicitação formal para mesclar (merge) uma branch dentro de outra, geralmente exigindo revisão e aprovação de outra(s) pessoa(s) antes de ser aceita. — o mecanismo central de revisão de código no Git. Um PR permite definir título, descrição, vínculo com itens de trabalho e revisores obrigatórios (pessoas que precisam aprovar antes do merge acontecer).

Políticas de branch

É comum ter uma branch de desenvolvimento e outra de implantação (frequentemente a main/master), que só recebe código já validado e pronto para produção. Para impor essa disciplina, é possível proteger uma branch: uma branch protegida não aceita commits diretos (só via pull request) e não pode ser excluída. As políticas de proteção mais relevantes incluem:

  • Número mínimo de revisores exigidos para aprovar o PR.
  • Impedir que o autor aprove sua própria alteração — completar seu próprio PR sem revisão externa anula o propósito da revisão.
  • Reset de votos quando novas alterações são enviadas depois de uma aprovação.
  • Vínculo obrigatório com um item de trabalho, garantindo rastreabilidade: todo código mesclado pode ser relacionado a um motivo documentado.
  • Exigir que comentários sejam resolvidos antes de concluir o PR.
  • Revisores automáticos, adicionados por padrão a todo PR (por exemplo, o líder técnico ou alguém de QA), inclusive com filtros por tipo de arquivo (ex.: só em alterações de *.html;*.css;*.js).
  • Validação de build — o pipeline de build precisa passar antes do PR poder ser concluído (aprofundado no Capítulo 5).
⚠ Qual branch é a "padrão"?

Ao clonar um repositório, a branch marcada como default é a que vem selecionada automaticamente. Faz sentido, na prática, definir a branch de desenvolvimento como padrão (em Project Settings → Repositories), para que novos clones já comecem no lugar certo, em vez de partirem direto da branch de produção.

Fluxo prático de um Pull Request

  1. Uma alteração é commitada e enviada (push) para uma branch de feature.
  2. Um pull request é criado, com revisores atribuídos (manualmente ou automaticamente).
  3. Os revisores comentam, aprovam, aprovam com sugestões, pedem mudanças ("wait for author") ou rejeitam.
  4. Na aba Files, o revisor compara o código antigo e o novo (lado a lado ou em linha) e comenta diretamente na margem.
  5. Com auto-completeAuto-complete (Pull Request)Opção que conclui automaticamente o pull request assim que todas as condições (aprovações, builds, comentários resolvidos) forem satisfeitas — sem precisar voltar manualmente para clicar em "concluir". habilitado, assim que todas as condições forem satisfeitas o PR é mesclado automaticamente, sem precisar de uma ação manual final.

Segurança de branch

Além das políticas gerais, é possível conceder permissões específicas por pessoa ou grupo em uma branch — por exemplo, a permissão "Bypass policies when completing pull requests", que permite ignorar as políticas em situações excepcionais (como uma correção urgente com a equipe de revisão indisponível). Esse tipo de permissão deve ser concedido com cautela.

Tags

Uma tagTagMarcador fixo que aponta para um commit específico no histórico do Git — ao contrário de uma branch, uma tag não recebe novos commits depois de criada. Útil para marcar versões, como v1.0. é um ponteiro fixo para um commit específico do histórico — como uma branch "congelada" — comumente usada para marcar versões (ex.: v1.0, beta-0.9.1). Usar tags em vez de branches para marcar versões ajuda a manter o número de branches sob controle.

ℹ Resumo do capítulo

O Repos oferece tudo o que se espera de uma ferramenta de controle de versão e CI/CD: branches, pull requests, comparação e revisão de código, e tags — tudo vinculável de volta aos itens de trabalho do Boards. A partir daqui, o código versionado está pronto para ser compilado e implantado automaticamente.

Capítulo 5

Build Pipelines

Com o código sob controle de versão, o próximo passo é compilá-lo automaticamente. Um build pipelineBuild pipelineSequência automatizada de etapas (restaurar dependências, compilar, testar, publicar) executada sempre que há uma mudança no código, garantindo que ele ainda "funciona" antes de seguir adiante. avisa a equipe imediatamente quando uma alteração quebra a compilação — o que, segundo o autor do livro, é onde reside a maior força prática do DevOps: reduz risco, economiza tempo e permite implantar a qualquer momento com o mínimo de indisponibilidade.

🏢 No condomínio

O build pipeline é a vistoria automática de obra que acontece toda vez que um material novo chega no canteiro: confere se está dentro das especificações, monta uma amostra de teste e só then libera o material para o próximo estágio. Se algo estiver fora do padrão, a vistoria barra ali mesmo — ninguém no condomínio fica sabendo só quando a parede já caiu.

O Azure DevOps oferece dois caminhos para criar um pipeline: o editor clássicoEditor clássico (Classic editor)Interface visual (sem código) para montar pipelines de build/release no Azure DevOps, arrastando e configurando tarefas prontas., mais visual e didático, ou pipelines em YAMLYAMLFormato de texto legível por humanos para configuração — o nome é um acrônimo recursivo de "YAML Ain't Markup Language". Um pipeline típico gerado pelo template ASP.NET Core tem uma sequência clássica de tarefas: Restore → Build → Test → Publish → Publish Artifact.

Rodando o build

Ao clicar em Save & queue, o build é colocado na fila e roda assim que um agente estiver disponível. Com apenas um agente hospedado gratuito, builds e releases concorrentes esperam sua vez — mais jobs paralelos podem ser comprados na seção de faturamento. Integração Contínua (CI) na prática

Na aba Triggers, a opção Enable continuous integration faz o pipeline disparar automaticamente a cada push em uma branch específica (com opção de incluir, excluir branches, ou filtrar por caminho de arquivo). A opção de "agrupar" (batch) mudanças evita disparar um build para cada commit individual quando vários chegam quase juntos — mais rápido, mas dificulta saber qual commit especificamente quebrou o build, caso aconteça. Também é possível agendar builds (por exemplo, todo dia às 5h da manhã) para detectar quebras causadas por dependências externas, mesmo sem mudança de código.

Pipelines em YAML

Ao criar um pipeline apontando para Azure Repos Git, o Azure DevOps oferece templates em YAML prontos. O arquivo resultante (azure-pipelines.yml) é commitado no próprio repositório — ou seja, o pipeline passa a ser versionado como código, junto do resto do projeto. A vantagem é rastreabilidade e reuso (copiar/colar entre projetos); a desvantagem é uma curva de aprendizado maior que o editor visual.

# Exemplo simplificado de pipeline YAML
trigger:
  - develop
pool:
  vmImage: 'windows-2019'
variables:
  buildConfiguration: 'Release'
steps:
  - task: DotNetCoreCLI@2
    displayName: Restore
    inputs:
      command: restore
  - task: DotNetCoreCLI@2
    displayName: Build
    inputs:
      arguments: '--configuration $(buildConfiguration)'

É possível alternar entre os dois mundos: o editor clássico tem um botão View YAML que exporta a configuração visual para um arquivo YAML equivalente — útil para migrar um pipeline existente sem reescrevê-lo do zero.

Segurança do pipeline

Como em projetos e repositórios, é possível gerenciar permissões específicas por pipeline — quem pode excluir builds, interromper execuções em andamento ou visualizar resultados — atribuindo essas permissões a grupos ou usuários individuais.

ℹ Resumo do capítulo

Build pipelines automatizam a verificação de que o código compila, passa nos testes e está pronto para virar um artefato implantável. O editor clássico é mais didático; o YAML trata o pipeline como código versionável. Agentes privados aceleram builds recorrentes e liberam controle total do ambiente de compilação.

Capítulo 6

Release Pipelines

Se o build pipeline garante que o código compila, o release pipelineRelease pipelinePipeline responsável por pegar o artefato gerado pelo build e efetivamente implantá-lo (deploy) em um ou mais ambientes, como desenvolvimento, teste, homologação e produção. cuida de implantar esse artefato nos ambientes certos, na ordem certa, com as aprovações certas.

🏢 No condomínio

Se o build pipeline é a vistoria do material, o release pipeline é a logística de entrega por andares: o material aprovado sobe primeiro para o "andar piloto" (ambiente de Development), depois, com aprovação do síndico, para o "andar de testes" (Test), e só por último, com aprovação final, para os andares ocupados (Production). Cada andar é um stageStage (estágio)Fase distinta de um release pipeline, tipicamente correspondendo a um ambiente (Development, Test, Acceptance, Production). do pipeline.

O editor de release

Ao criar um novo release pipeline, escolhe-se um template — vários já prontos para implantação em Azure App ServiceAzure App ServiceServiço do Azure para hospedar aplicações web, APIs REST e back-ends móveis sem precisar gerenciar servidores diretamente. Diferente do build, o editor de release não oferece a opção YAML — trabalha só de forma visual (isso muda com o recurso de Environments, visto adiante).

Cada pipeline de release consome um artefato — normalmente o artefato de um build pipeline específico, mas também pode vir diretamente de um repositório Git, GitHub ou até Jenkins.

Existem contornos usando condições e aprovações, mas o autor afirma preferir, por enquanto, o release pipeline clássico para esse cenário.

Segurança de pipelines de release

Assim como nos build pipelines, é possível gerenciar quem pode excluir, parar ou visualizar releases, atribuindo permissões a grupos e usuários específicos.

É o módulo menos usado do pacote, segundo o autor, mas cobre uma etapa que a automação de testes unitários (dentro do pipeline) não substitui: o teste manual, exploratório e de aceitação.

🏢 No condomínio

O Test Plans é a vistoria de qualidade antes da entrega das chaves — um checklist detalhado que confere item por item (torneira pinga? luz acende? porta fecha certo?) antes de liberar o apartamento para o morador. Diferente da vistoria automática de material (build), aqui é uma pessoa de carne e osso testando o resultado final na prática.

Habilitando o Test Plans

Contas gratuitas (Basic) têm acesso limitado ao Test Plans; o recurso completo exige um plano pago ou um trial gratuito de 30 dias, habilitável em Billing. Assinantes Enterprise, Test Professional ou MSDN Platforms já têm acesso completo por padrão.

No plano gratuito: testes ligados a tarefas do board

Sem o plano pago, testes são criados como tasks do tipo test dentro de um item do backlog (Product Backlog Item, User Story etc.), aparecendo em uma suíte de teste automática. Cada teste pode ser executado manualmente (marcando passou/falhou), com opção de anexar comentários, capturas de tela e até abrir um bug diretamente a partir de um teste que falhou.

Gráficos e relatórios

A aba Chart permite montar gráficos de pizza, coluna, barra ou linha sobre os casos de teste — por exemplo, um gráfico de pizza agrupado por Outcome (resultado: passou/falhou/bloqueado) dá uma visão instantânea da saúde dos testes daquele ciclo. A aba Progress report resume rapidamente quantos testes estão abertos, quantos passaram, quantos falharam e qual a porcentagem já executada.

No plano pago: gestão completa de casos de teste

Planos pagos desbloqueiam a aba Define, permitindo criar casos de teste diretamente no Test Plans (não apenas via task no board), inclusive em uma interface de grade parecida com uma planilha, onde múltiplos testes e seus passos podem ser digitados de uma vez.

Parâmetros

Um conjunto de parâmetrosParameter setConjunto de valores de teste reutilizáveis (ex.: diferentes quantidades, nomes, valores nulos) que podem ser referenciados dentro dos passos de um caso de teste, garantindo cobertura sistemática de casos de borda. permite testar a mesma ação com vários valores diferentes — por exemplo, testar um campo de "quantidade" com 0, 1, 256, -1, vazio e nulo, cobrindo casos de borda de forma sistemática.

Configurações

Uma configuração de testeTest configurationCombinação específica de variáveis de ambiente (ex.: sistema operacional, navegador, placa de vídeo) sob a qual um conjunto de testes deve ser executado. combina variáveis de ambiente (sistema operacional, navegador, placa de vídeo etc.). Associar múltiplas configurações a uma suíte de teste multiplica automaticamente o número de execuções necessárias — por exemplo, testar em dois navegadores dobra a quantidade de testes a rodar, cobrindo cenários cross-platform de forma organizada.

ℹ Resumo do capítulo

O Test Plans transforma testes manuais em um processo rastreável e mensurável, com integração direta ao Boards (feedback imediato aos desenvolvedores via bugs vinculados) e recursos de relatório que dão visibilidade a todo o time sobre a real qualidade do que está sendo entregue.

Artifacts

O último módulo, e talvez o mais subestimado segundo o autor, é o ArtifactsArtifactsMódulo do Azure DevOps para hospedar pacotes de software reutilizáveis (feeds), com suporte a NuGet, npm, Maven e Python.: um repositório privado de pacotes reutilizáveis — pense em bibliotecas de código compartilhadas entre vários projetos, sem precisar publicá-las em um repositório público.

🏢 No condomínio

O Artifacts é o almoxarifado central de peças padronizadas do condomínio — parafusos, dobradiças, torneiras do mesmo modelo usado em todos os apartamentos. Em vez de cada equipe de manutenção comprar (ou fabricar) sua própria peça toda vez, todo mundo retira do mesmo estoque compartilhado, com controle de versão de cada lote.

Feeds

Um feedFeed (Artifacts)Repositório de pacotes dentro do Azure DevOps Artifacts — pode ser específico de um projeto ou compartilhado por toda a organização. é criado automaticamente por padrão, com escopo de organização (visível em todos os projetos, sempre privado). Novos feeds criados manualmente têm escopo de projeto por padrão (públicos se o projeto for público). Um feed pode ter fontes upstreamUpstream sourcesConfiguração que permite ao feed buscar automaticamente pacotes de fontes públicas externas (como o NuGet.org) e mantê-los em cache local, evitando dependência direta da fonte externa. habilitadas — o feed passa a "espelhar" pacotes públicos automaticamente, útil como cache, mas consome o limite gratuito de armazenamento (2 GB).

Conectando-se a um feed

Existem três formas de autenticação para publicar e restaurar pacotes: diretamente pelo Visual Studio (via Package Manager Settings), pelo .NET Core CLI.NET Core CLIFerramenta de linha de comando do .NET Core/.NET, usada para compilar, testar, publicar e gerenciar pacotes de projetos .NET. com usuário e senha, ou usando um Personal Access Token (PAT) em vez de senha — mais seguro e recomendado para automação.

Publicando pacotes

Criar um pacote NuGetPacote NuGetArquivo compactado (.nupkg) contendo uma biblioteca .NET compilada e seus metadados, pronto para ser referenciado por outros projetos. exige apenas marcar a opção GeneratePackageOnBuild no projeto .NET — o build passa a gerar automaticamente um arquivo .nupkg. Publicá-lo no feed pode ser feito via linha de comando (dotnet nuget push) autenticado com PAT, ou usando o Azure Artifacts Credential Provider, que evita digitar o token repetidamente ao lembrar as credenciais após o primeiro login.

⚠ Versões não se repetem

Não é possível publicar duas vezes o pacote com exatamente a mesma versão — republicar exige incrementar o número de versão. Isso vale também em pipelines automatizados: um push de uma versão já existente falha, a menos que a tarefa NuGet tenha a opção "Allow duplicates to be skipped" habilitada.

Publicando e restaurando via pipeline

Publicar pacotes automaticamente é apenas trocar a tarefa de "publish" por um "push" no pipeline de build. Para restaurar (baixar) pacotes do feed interno como dependência de outro projeto, a tarefa Restore precisa apontar explicitamente para o feed correto (feedsToUse: 'select' e o ID do feed) — caso contrário, o build falha ao não encontrar o pacote em fontes públicas externas.

ℹ Resumo do capítulo

O Artifacts fecha o ciclo do Azure DevOps: além de planejar (Boards), versionar (Repos), compilar/implantar (Pipelines) e testar (Test Plans), o time ganha um repositório privado e versionado para reutilizar código entre projetos, com integração nativa aos pipelines de build e release.
